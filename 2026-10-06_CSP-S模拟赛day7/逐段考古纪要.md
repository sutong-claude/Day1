## E-D7-013｜B 45 RE 根因闭合｜不是“只是慢”，而是无用 unordered_set 造成 O(n²) 峰值内存

**来源**：
- OJ B 正式 submitted source；
- OJ 逐点表；
- 题面原始页面（memory limit = **256MiB**）；
- 2026-10-07 用正式 source 构造最坏链树实测 RSS；
- 256MiB 虚拟内存限制下复现实验。

### 正式代码里的关键结构 [P/source]

`calc`：

```cpp
inline int calc(int root, unordered_set<int>& st, int fa, int mi) {
    st.insert(root);
    mi=min(mi,a[root]);
    for(auto y:e[root])
        if(!vis[y] && y!=fa)
            mi=min(calc(y,st,root,mi),mi);
    return mi;
}
```

而 `dfs`：

```cpp
for(auto y:e[root]) {
    if(vis[y]) continue;
    unordered_set<int> mp;
    int m=calc(y,mp,root,n+1);
    dfs(root,m);
}
```

最关键事实：
> `mp` 在 `calc` 结束后**完全没有被读取**。

它只负责插入整个当前连通块的节点，却没有参与任何算法判定。

更糟的是：
> 下一层 `dfs(root,m)` 发生在当前 loop iteration 结束、`mp` 析构之前。

所以祖先层的所有 `unordered_set` 会在深递归期间同时存活。

### 最坏构造

树：

```
1-2-3-...-n
```

优先级：

```
p = 1,2,3,...,n
```

每层负责人都删链端点。

于是：
- 第1层 `mp` 插入 n-1 个节点；
- 第2层插 n-2；
- ...
- 同时存活量近似：

```
(n-1)+(n-2)+...+1 = Θ(n²)
```

而这些还是高额 overhead 的 `unordered_set` node + bucket。

### 256MiB 限制下直接复现 [E]

对 n=3300 链，用正式源码 + 256MiB 虚拟内存限制：

```
terminate called after throwing std::bad_alloc
SIGABRT
```

这正是 Runtime Error 类型。

### 修订结论

以前只写：
> “B 是朴素递归，复杂度瓶颈在 calc 重扫。”

还不够完整。

准确应拆成：

```
time complexity:
重复 calc 连通块扫描
→ 最坏 Θ(n²)

memory implementation bug:
每层还把整个 component 塞进完全不用的 unordered_set
+ 递归发生在 set 析构之前
→ 同时驻留 Θ(n²) 个 hash nodes
→ 256MiB 前先 bad_alloc / RE
```

所以最终 **45 RE** 不是“本来会 TLE，只是判成 RE”这么简单：
> 它在中等规模已经先被一个纯实现的 O(n²) 峰值内存 bug 杀掉。

### 为什么 45 分恰好合理

- subtask1：Σn≤10 → 20 AC
- subtask2：Σn≤2000 → 25 AC
- subtask3：开始出现 227MiB RE
- 所以总分停在 **20+25=45**

这与正式 score 完全闭合。

### 如果比赛时只做一个最小修补

删掉 `unordered_set st/mp`：
- **不会改变 calc 返回的 mi 语义**；
- 能把这部分 Θ(n²) retained hash memory 直接消掉。

但它仍然：
- 重复扫描 component；
- 最坏时间 Θ(n²)；
- full n≤1e5 / Σn≤1e6 仍不够。

所以这只是：
> **RE → 可能继续拿中档 / 转 TLE**

而不是 full 解。

full 突破仍是 E-D7-007：
> 删除分裂难维护 → 倒序加入 → DSU / 时间反演。
