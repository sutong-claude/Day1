## E-D7-013｜B 45 RE 根因闭合｜不是“只是慢”，而是无用 unordered_set 造成 O(n²) 峰值内存

**来源**：
- OJ B 正式 submitted source；
- OJ 逐点表；
- 题面原始页面（memory limit = **256MiB**）；
- 2026-10-07 用正式 source 构造最坏链树实测 RSS；
- 256MiB 虚拟内存限制下复现实验。

### 正式代码里的关键结构 [P/source]

`calc`：

```cpp
inline int calc(int root, unordered_set<int>& st, int fa, int mi) {
    st.insert(root);
    mi=min(mi,a[root]);
    for(auto y:e[root])
        if(!vis[y] && y!=fa)
            mi=min(calc(y,st,root,mi),mi);
    return mi;
}
```

而 `dfs`：

```cpp
for(auto y:e[root]) {
    if(vis[y]) continue;
    unordered_set<int> mp;
    int m=calc(y,mp,root,n+1);
    dfs(root,m);
}
```

最关键事实：
> `mp` 在 `calc` 结束后**完全没有被读取**。

它只负责插入整个当前连通块的节点，却没有参与任何算法判定。

更糟的是：
> 下一层 `dfs(root,m)` 发生在当前 loop iteration 结束、`mp` 析构之前。

所以祖先层的所有 `unordered_set` 会在深递归期间同时存活。

### 最坏构造

树：

```
1-2-3-...-n
```

优先级：

```
p = 1,2,3,...,n
```

每层负责人都删链端点。

于是：
- 第1层 `mp` 插入 n-1 个节点；
- 第2层插 n-2；
- ...
- 同时存活量近似：

```
(n-1)+(n-2)+...+1 = Θ(n²)
```

而这些还是高额 overhead 的 `unordered_set` node + bucket。

说明 RE 强烈依赖树形 / 删除顺序造成的峰值 set 累积，而不是“n到了某个数必炸”。

### 256MiB 限制下直接复现 [E]

对 n=3300 链，用正式源码 + 256MiB 虚拟内存限制：

```

```

这正是 Runtime Error 类型。

### 修订结论

以前只写：
> “B 是朴素递归，复杂度瓶颈在 calc 重扫。”

还不够完整。

准确应拆成：

```
time complexity:
重复 calc 连通块扫描
→ 最坏 Θ(n²)

memory implementation bug:
每层还把整个 component 塞进完全不用的 unordered_set
+ 递归发生在 set 析构之前
→ 同时驻留 Θ(n²) 个 hash nodes
→ 256MiB 前先 bad_alloc / RE
```

所以最终 **45 RE** 不是“本来会 TLE，只是判成 RE”这么简单：
> 它在中等规模已经先被一个纯实现的 O(n²) 峰值内存 bug 杀掉。

### 为什么 45 分恰好合理

- subtask1：Σn≤10 → 20 AC
- subtask2：Σn≤2000 → 25 AC
- subtask3：开始出现 227MiB RE
- 所以总分停在 **20+25=45**

这与正式 score 完全闭合。

### 如果比赛时只做一个最小修补

删掉 `unordered_set st/mp`：
- **不会改变 calc 返回的 mi 语义**；
- 能把这部分 Θ(n²) retained hash memory 直接消掉。

但它仍然：
- 重复扫描 component；
- 最坏时间 Θ(n²)；
- full n≤1e5 / Σn≤1e6 仍不够。

所以这只是：
> **RE → 可能继续拿中档 / 转 TLE**

而不是 full 解。

full 突破仍是 E-D7-007：
> 删除分裂难维护 → 倒序加入 → DSU / 时间反演。


## E-D7-014｜B 最小修补反事实｜只删无用 set，可把 RE 消掉并让 n≤1e4 进入可跑区间

**来源**：
- E-D7-013 的正式 source；
- Day7 VM 中 B 的 1-1 / 2-1 / 3-1 / 4-1 附件；
- 仅删除 `unordered_set` 参数/插入，不改变 `calc` 返回 mi 与递归逻辑的最小 patch；
- 本地最坏链压力。

### patch 的语义

原来：

```cpp
unordered_set<int> mp;
int m = calc(y, mp, root, n+1);
dfs(root,m);
```

且 `mp` 从不读取。

最小 patch 只做：

```cpp
int m = calc(y, root, n+1);
dfs(root,m);
```

并删掉 `calc` 中的：
```cpp
st.insert(root);
```

所以：
> **算法选择负责人 mi 的数学语义没有改变。**

这不是赛后换算法，只是删掉无用 retained state。

### 附件实测 [E]

| 附件 | patch结果 |
|---|---|
| 1-1 | 与参考输出逐 token match |
| 2-1 | match |
| 3-1 | match，约 0.05s / 25MiB |
| 4-1 | 15s 内未完成全部 testcase，只输出前若干组 |

说明：
- 小/中档 correctness 没被 patch 改坏；
- 第4档仍然被 Θ(n²) 时间拖住。

### 最坏链压力

同样使用：
- path tree `1-2-...-n`
- `p=1,2,...,n`

仅删 set 后：

| n | time | RSS |
|---:|---:|---:|
| 5,000 | ~0.10s | ~25MiB |
| 10,000 | **~0.35s** | ~26MiB |
| 15,000 | ~0.75s | ~27MiB |
| 20,000 | ~1.33s | ~28MiB |

对比正式版 n=3000 已约 216MiB。

因此：
> 内存 bug 一删，`Σn≤10^4` 级最坏单链至少在当前环境已经进入非常轻的内存、亚秒级时间范围。

### 对分数机会成本的谨慎结论

正式题面表的第3行 HTML 本身存在缺失/错位，归档没有可靠显示该档分值；但总题分100，而已明确：
- subtask1 =20
- subtask2 =25
- subtask4 =30

因此剩余档从总分算应为25，**但这里只把它作为推算，不冒充原页面明确字段**。

可以可靠说：

> 正式 45 分之后的第3档 RE，很可能主要被这个无用 set 内存 bug 阻断；最小 patch 已在同档附件和 n=10^4 最坏链上证明“不会再因该内存机制炸掉”。

不能直接说：
> “比赛时删一行就必得70。”

因为隐藏数据、机器速度和第3档 HTML 缺失分值仍未全部直接验证。

### 赛时触发器

当 profiler / 观察已经指出：
> 真正需要的是 `calc` 返回一个最小 rank

而某个容器：
- 被完整填充；
- 之后一次都不查询；

必须立刻删掉它再跑一次。

**“为了以后可能有用先存下来”在递归里尤其危险。**
局部无用状态 + 深递归 = 峰值内存可能从 O(n) 变 O(n²)。

对所有无序叶子对 ((A,B))：
1. 找树上简单路径；
2. 计算路径长度 `dist(A,B)`；
3. 对每个点求到该路径的最短距离；
4. 取最大值为 H；
5. 最大化 `H * dist(A,B)`，同时数达到最大值的叶子对。

小树上可以直接穷举，完全不依赖 03:48 候选的任何内部假设。

### 第一层：n=2 就暴露 H=0 边界错误 [X]

输入：

```text
2
1 2
```

唯一叶子对就是 1-2：
- 主路线覆盖整棵树；
- H=0；
- 长度=1；
- 正确：`0 1`。

03:48 候选实际输出：

```text
1 2
```

原因直接在源码：

```cpp
int ma = 1;
...
int tot = ma1 + ma2;
tot = max(tot, 1LL);
```

它把两个本可为 0 的几何量强行钳成至少 1。

但这只算边界实现错，还不足以否定核心模型。

### 第二层：即使不看 H=0，n=5 已有**正值核心模型反例** [E/X]

树：

```text
3
 \
  1 - 2 - 5
 /
4
```

边：

```text
3 1
4 1
1 2
2 5
```

叶子：3、4、5。

#### 真正最优

选路线 3-1-4：
- 路线长度 = 2；
- 点5到路线距离 = 2；
- H = 2；
- 指标 = 4。

其他两条叶子路线：
- 3-1-2-5
- 4-1-2-5

长度都是3，但剩余另一短叶到路线距离只有1：
- 指标 = 3。

所以：
- 正确输出 = **`4 1`**；
- 唯一最优路线 = (3,4)。

#### 03:48 候选

实测：

```text
3 4
```

也就是：
- 最大值本身错；
- 路线计数也错。

### 核心错误：把“最长支路”固定拿去做路径长度

候选在每个点 i：
- parent-side 最大深度 → `ma`；
- child-side 只取两条最大深度 → `ma1,ma2`；
- 然后固定：
  `res = ma * (ma1+ma2)`。

这隐含：
> 两条最深 child branch 应该拿来组成主路线，
> parent side 留作 H。

n=5 反例正好说明这个贪心方向可以完全相反：

```
长支路 1-2-5
若拿去做 path:
  长度变3
  但 H只剩1
  product=3

若故意把长支路留在 path 外:
  path 只用两条短支路 3-1-4
  长度2
  H反而变2
  product=4
```

所以：
> **路径长度与 H 是竞争资源，不可以各自独立取“最大”。**

这不是改 `max(...,1)`、修 depth 初值能解决的。

### 第三层：计数对象也不对

n=4 星形：

```text
  2
  |
3-1-4
```

任意两片叶组成的路线：
- len=2；
- 第三片叶到路线距离=1；
- 最大值2；
- 正确最优路线数 = C(3,2)=3。

候选却按“哪个中心/节点 i 产生 res”计数，而不是按叶子对计数。

因此：
> **cnt++ 的对象从根上就是“候选中心”，不是题目要求的“主路线”。**

### 为什么 03:51 “算法不可行”判断是正确的

此前只知道：
- 样例跑错；
- 多轮 parent/dfs/top1/top2 修补无效；
- 本人最后判断模型死。

现在最小反例证明：
1. H=0 有边界实现错；
2. 正值 n=5 已有核心 trade-off 反例；
3. 计数对象也不匹配题意。

所以 03:51 的“不是再修一个实现 bug，而是模型不可行”可以升级为 [E/X] 强证据。

### 赛时更好的止损动作

一旦候选结构长成：

```
best = maxA * maxB
```

且 A/B 来自同一批分支的互斥选择，
必须先问：

> “把最大元素用于 A，会不会导致 B 失去它？”

最小检查就是三叉树/四叉树：
- 两短一长；
- 三条相近；
- H=0 的纯链。

这种局部 trade-off 反例，比继续对大样例 Debug 更快杀模型。
