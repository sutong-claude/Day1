# 3. 这张表推翻了什么

旧版复盘曾把 A 后到最后大体压成：

> “B 一直吞掉后半场，最后25分钟才碰D。”

raw_keys 明确不支持这个叙述。

真正形态更像：

```text
A编码高峰
↓
B读题/建模
↓
B brute编码高峰
↓
B调试/优化
↓
约120～195分钟长时间几乎无编码：C/D读题、口述、手玩、B离线思考
↓
约195分钟后D突然进入大规模编码
↓
最后30分钟F9密集Debug
```

也就是说：

> **后半场不是“机械写B三小时”，而是发生过明显的研究模式切换。**

# 4. B 的 Debug 特征

75–90分钟：
- F9 11 次；
- 键盘量不算高；
- 与录音中的递归自调用、父亲锁死、执行路径调试吻合。

这段属于典型：

> **代码主体已经有了，主要在 Debugger 里验证执行。**

而不是还在大量写新算法。

90–120分钟：
- F9继续；
- 方向键较多；
- file_changes 在 95分钟附近形成1433B稳定版；
- 之后有失败重写再回滚。

所以 B 的稳定 brute 冻结是有多源证据的。

# 5. C/D 研究为什么在 final cpp 里看不出来

120～195分钟整个75分钟区间 keydown 极少。

如果只读源码，会误判：

> “这一小时几乎什么都没做。”

但录音同期恰好包含：
- C 概率题手算；
- v=50 性质；
- 切 D；
- D N≤100 暴力；
- D 5000 优化猜想；
- 回 B 思考离线。

所以这场是捕捉器设计目标最典型的案例：

> **源码变化少，不代表研究产出少。**

raw_keys 的低活动 + 录音高密度推理，反而说明当时主要产出在脑图/口述而不是代码。

# 6. D 的最后 Debug 黑洞

195–210分钟：
- 1546 keydown；
- 190 Backspace；
- 217 方向键；

说明 D 开始快速实现。

210–225分钟：
- F9 达15次，是全场最高15分钟窗口；

和 screen / 录音中：
- Debugger 单步；
- “为什么代码不按照我的执行”；
- 反复进入库函数；

完全吻合。

最后在03:51口头判定算法不可行，随后把1663B候选推倒。

# 7. Ctrl+S / 文件快照的关系

Ctrl+S 不是所有保存动作的唯一来源，但能看到几个高密集区：
- A 16～36分钟；
- B 64～113分钟；
- D 207～233分钟。

这和 file_changes 的 T1/T2/T4 主要版本区间一致。

# 8. 以后 raw_keys 怎么用

不做低价值的“你按了多少个A键”。

只做三类高价值问题：

1. **研究模式识别**：高输入 / 高F9 / 低输入+高口述；
2. **Bug时间定位**：某个 file change 前后 Backspace/F9 是否爆发；
3. **交付链核对**：最后保存、复制、freopen、提交前有没有重新编辑。

# 9. 一句话

> **Day7 的 raw keyboard 进一步证明：真正的问题不是“B一直写到最后”，而是研究成果在多个模式间切换后，C10/D19这两份已经想明白的资产始终没有进入代码冻结状态。**
