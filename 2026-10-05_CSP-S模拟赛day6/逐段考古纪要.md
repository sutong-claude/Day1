## E-D6-002｜00:55～01:45｜B 计算日志｜图/DAG方向不是无效尝试

**来源**：录音 +代码。  
**赛时结构**：日志点、compatibility、DAG、最长链。  
**真正瓶颈**：pair compatibility 若 O(m²) 验证太慢。

`t_j-t_i ≥ F(x_j)-F(x_i)`

**结论**：赛时已经在正确“最长兼容子序列”方向，缺的是把 pair 条件做势函数变换。

## E-D6-004｜C 反馈灯阵｜四分类赛时其实已经出现

**来源**：二次复盘 + 录音/代码版本。  
固定最终亮灯数 k 后，点按是否包含 k-1 / k 应分四类：
1. 同时包含：必须亮；
2. 只含 k-1：可选亮；
3. 只含 k：不可行；
4. 都不含：必须灭。

**赛时真实失误**：最后把第1类和第2类都压成一个 cnt，丢掉 forced/optional 的语义差别。  
**结论**：不是“没想到分类”，而是**信息压缩过度**。  
**触发器**：两个状态在后续约束中的角色不同，就不能只因为当前都“计数+1”而合并。

## E-D6-005｜D 频段配对｜15分是标准正确 brute

**来源**：OJ record + code audit。  
**最终分**：15 TLE，subtask1 全 AC。  
**赛时修复**：phi helper CE、i*j→p[i]*p[j]、剩余质因子、phi(1)、x>0→x>1 等。  
**结论**：模型正确、复杂度不足，是应该冻结的 partial，而不是“失败代码”。  
**可扩一档**：n≤1000 可先筛 phi(p_i p_j) / 预处理 pair 值，再做区间 DP `best[l][r]`，O(n²) 预处理、O(1) query。

## E-D6-010｜C 四分类出现的具体版本窗口

**来源**：T3 31 个保存状态。

四分类代码形态在约 13:30:20 首次明显出现，13:31～13:32 发生反复：

```
同时包含(k-1,k)
只包含(k-1)
只包含(k)
都不包含
```

其中一版把“同时包含”和“只含 k-1”都 `cnt++`，另一版甚至把“只含 k”也暂时 `cnt++`；随后整个四分类又被删回单条件。

[P/source] 因此：
> C 不是从头到尾都没有正解结构；正确分类曾真实进入代码，但没有保护类别语义，后来发生了信息退化。

这类退化以后应触发“语义 checkpoint”：
- 新增分类时写下每类含义；
- 后续压缩前必须证明等价；
- 未证明不能为了代码短而合并状态。
