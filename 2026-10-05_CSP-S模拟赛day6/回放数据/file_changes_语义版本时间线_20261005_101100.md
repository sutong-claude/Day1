# 3. B｜12分钟内修干净实现层，但数学 predicate 仍然错

B 只有 6 次主文件保存，变化非常集中。

## B0｜12:34:00，1281B

首个可见主体同时存在多类实现错误：
- 全局测试组数 `int t` 与日志时间数组 `t[]` 重名；
- 未完成/错误的二分 helper；
- 路段最短时间用整数除法；
- `if (x != work)` 把数组名和标量比较；
- 日志检查循环写成 `i<=n` 而输入日志数是 `m`；
- 更根本地，把可变速/最大速率约束压成固定平均速度 `l/tend`。

## B1～B3｜12:34:31～12:34:58

短时间内连续：
1. 删除坏掉的 helper；
2. 测试组数 `t→T`；
3. `x→x[i]`。

这些都是实现/编译层修补。

## B4｜12:43:56

又把：
- `lst` 改成 double；
- 路段时间改成 `1.0 * distance / u[i]`；
- 平均速度/位置比较改 double。

到这里程序已经“更像能跑的程序”。

## B5｜12:45:51，1107B

加入正式 `WOWO.in/out`，源码逐字对应 OJ WA0 提交。

### 关键诊断 [P + X]

这条链很有教学价值：

> **实现层在快速变好，但数学模型并没有随之变真。**

因此 B 是“Debug 能把程序从 CE/类型错误修到稳定运行，却不能救一个错误 predicate”的标准反例。

触发器：
> 如果连续 3 次修补都只改变类型、下标、编译、IO，却没有增加新的数学不变量/反例/必要充分性证明，必须暂停 Debug，回到模型层。

# 4. D｜与 B 相反：微型探针确实在修数学实现契约

D 有 11 次保存，前 10 次在约 8 分钟内完成。

## D0｜12:54:52

首版存在三个明确实现错误：
- Euler phi 更新误写成数组 `p`；
- 枚举对计算 `i*j` 而不是 `p[i]*p[j]`；
- 分解后剩余大质因子未正确处理。

## D1～D3｜12:55:04～12:56:32

依次：
1. 修 `ans*(i-1)/i`；
2. 增加剩余因子处理，但先写成错误条件 `x>0`；
3. 修 `i*j → p[i]*p[j]`。

## D4～D6｜12:58:13～12:59:09

这里不是“乱改代码”，而是主动把正常答案输出注释掉，依次只打印：

```
phi(1)
phi(2)
phi(6)
```

这是非常清晰的 **最小微型探针**：
- 先测边界1；
- 再测素数2；
- 再测含多个质因子的6。

## D7～D8｜12:59:35～13:02:06

探针直接推动两次契约修复：
- `x==1 → return 1`；
- 剩余因子条件 `x>0 → x>1`。

# 5. C｜31 次保存中的“正确分类 → 错误压缩”可被精确定位

C 共 31 次保存 / 25 unique。

关键节点：

| save index | 约时刻 | bytes | 含义 |
|---:|---:|---:|---|
| 1 | 13:10:50 | 956 | 起始 brute，枚举区间配置 |
| 8 | 13:18:40 | 955 | 修正枚举/计数索引 |
| 11 | 13:30:20 | 1202 | 首次明显写出“双状态四分类”代码形态 |
| 14 | 13:31:14 | 1202 | 修正 `v=i-1` 后再次出现四分类 |
| 15 | 13:31:27 | 1207 | 将“只含 i”一类也压进 cnt |
| 16 | 13:32:00 | 1191 | 又撤回这一压缩 |
| 17 | 13:32:41 | 975 | 四分类整体被删回单条件 |
| 23 | 13:36:27 | 1231 | 加入模逆/期望式输出框架 |
| 30 | 13:39:33 | 1227 | 正式 IO 版，逐字对应 OJ TLE0 source |
| 31 | 13:41:11 | 1231 | 提交后又把 freopen 注释掉 |

四分类阶段代码明确区分：
- 同时包含 `k-1` 与 `k`；
- 只包含 `k-1`；
- 只包含 `k`；
- 两者都不包含。

问题不是“完全没发现结构”，而是这些类别后来被压成了一个 `cnt`，类别的 forced / optional / impossible / off 语义没有被保留。

[P/source] 这把旧结论进一步加强成：
> **C 的失败不是研究量不足，而是正确结构出现后没有保护语义，最终回退成更弱 predicate。**

# 6. 四题的提交后工作区漂移

Day6 至少 C、D 都存在：
- OJ submit source 与某个 file_changes snapshot 精确一致；
- 后面 VM 工作区继续变化。

因此新增硬规则：

```
“最终磁盘文件”
!=
“正式提交文件”
```

以后自动化必须优先做：
1. OJ source hash；
2. file_changes snapshot 内容比对；
3. 找到唯一/最近匹配版本；
4. 再讨论“提交后又改了什么”。

不要用比赛结束时的 VM 文件覆盖正式提交历史。
