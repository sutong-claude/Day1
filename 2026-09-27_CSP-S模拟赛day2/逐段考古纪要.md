## E-D2-001｜A 乘法前半段｜“能解释”没有替代真值

**来源**：录音 + 历史代码。  
**赛时多代**：数1个数 → 连续1段 → 改系数 → 最终有符号二进制思路。  
**问题**：多次出现“我认为我的思路没有问题”，但大样例答案不一致。

## E-D2-002｜暴力为什么晚了约2小时

**来源**：录音自述。  
本人给出三条原因：
1. 知道错但没有小反例；
2. 能给当前公式合理解释；
3. 一开始写出的等式其实已经可以枚举，却没把它识别成 brute。

**核心病因**：把暴力只理解成“数据小的骗分代码”，没理解成“替自己算真值/自动找小反例的研究工具”。  
**迁移**：任何 答案=min/max over X，只要 X 可枚举，就先写真值，不受原题 n 大小影响。

## E-D2-008｜A 对拍 oracle 边界复核｜1e4 人工截断在 generator 全域内是安全的

**来源**：
- 三包原始 `duipai_T1/gen.cpp`
- 三包原始 `duipai_T1/ac.cpp`
- 2026-10-07 独立扩域穷举复核

### generator 的真实定义域 [P/source]

`gen.cpp` 只生成：
- 二进制串；
- 长度 1..10。

因此转成整数后：
```
ans ∈ [0, 1023]
```

### oracle 的可疑点

`ac.cpp` 的真值搜索是：
```cpp
for (int i = 0; i <= 10000; ++i)
    minimize popcount(i) + popcount(i + ans);
```

`i<=10000` 是人工截断，不能因为文件名叫 `ac.cpp` 就默认正确。

### 本轮独立验证 [E]

对 generator 的完整数值域 `ans=0..1023`，逐个比较：

```
min_{0<=i<=10000}
vs
min_{0<=i<=65535}
```

结果：
- 1024 个 ans；
- mismatch = **0**；
- 扩展搜索中“第一次达到最优值”的 i 最大仅 **170**。

### 修订结论

Day2 A 后半段启动对拍后，至少在实际 generator 覆盖域里，**oracle 并没有因为 1e4 截断制造假真值**。

所以 Day2 A 的积极经验可以写得更强：
> 真正启动 brute/gen 后，这套研究工具不仅“存在”，而且在实际 generator 定义域内经独立穷举复核是可靠的。

但边界必须保留：
> 这不证明 `i<=10000` 对任意更长二进制输入都充分；oracle 的可靠性必须和 generator domain 一起陈述。

完整审计：
`tools/archive/Checker_Stress_Oracle源码审计_2026-10-07.md`

## E-D2-009｜D checker 再审计｜赛时漏枚举不是 isValid 的锅

**来源**：三包原始 `chk.cpp` 完整源码。

checker 的 `isValid` 会逐人验证：
- 狼不能相邻；
- 非狼村民按照 L/R 观察两个指定位置；
- 越界位置按好人处理；
- 实际看到的狼数必须等于 b[i]。

同时：
- candidate 输出 -1、jury 有解 → WA；
- candidate 给出 assignment → 完整调用 `isValid`；
- jury=-1 而 candidate 找到合法解 → checker FAIL。

因此 [P/source]：
> Day2 D 赛时 0 分暴力的已知根因仍是“mask 转 wolves 数组时未补满 n 位，枚举空间缺失”，不是 checker/helper 漏验。

这也是一个反例：**读 checker 有价值，但必须继续区分 checker 契约与 candidate 自己的枚举器。**

## E-D2-012｜D 第一交漏一半 mask 的原因可以精确到 vector 长度

D1：

```cpp
int t=i;
wolves.clear();
while (t != 0) {
    wolves.push_back(t % 2);
    t /= 2;
}
```

而 `isValid` 首先检查：

```cpp
wolves.size() == n
```

所以一个 mask 想真正进入语义验证，最高位必须已经到第 n 位。

也就是：
> 实际只覆盖 `i in [2^(n-1),2^n-1]` 那半个空间。

这比“少补几个0”更精确：
**漏的是最高位为0的整整一半 assignment。**
