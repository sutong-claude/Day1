# 虚拟机赛场工程经验：把 NOI Linux 做成比赛设备

七场已经证明，VM 不是背景，而是比赛系统的一部分。

## 1. 已真实出现过的工程事故

- Code::Blocks F9 编译的不是屏幕上正在看的文件；
- Debug / Release target 混淆；
- 终端窗口一闪而退 / 多开；
- 剪贴板困难导致长命令手敲；
- 鼠标被 VM 抓住；
- 时区错 12 小时；
- Sublime 更新提示干扰；
- VM / 主机磁盘压力；
- 录音/录像临时文件把磁盘拖爆；
- 桌面 BAG 与仓库版本漂移；
- 错格式测试数据进入验证链。

这些都可能直接把算法能力转换成 0 分。

---

## 2. 最重要原则：同一题只有一个 main.cpp

Code::Blocks、终端样例、sanitizer、stress、最终提交都必须围绕同一份：

`T?/main.cpp`

不再允许：
- 独立 debug/main.cpp 作为另一个 candidate；
- problems/T1.cpp 和 T1/main.cpp 并存；
- 屏幕改 A、F9 编译 B；
- stress 用的 candidate 和最终提交不是同一份。

BAG V4 就是在工程层消灭“代码身份不确定”。

---

## 3. 程序慢先判复杂度，不先怪 VM

历史上曾把 7 秒误判为“虚拟机核少”。

但单线程 O(n^3)：
- 多给核没帮助；
- 换云服务器也可能一样慢。

所以赛场诊断顺序：

```text
慢
→ 先估复杂度 / 重复工作
→ 再排查 I/O / sanitizer / 编译模式
→ 最后才怀疑 VM 性能
```

不要用“机器慢”掩盖算法复杂度。

---

## 4. 磁盘是比赛资源

Replay / screen / 录音 / 大样例都吃磁盘。

合理保护顺序：

```text
磁盘水位过低
→ 先停高体积 screen
→ 保留 timeline / file snapshots / raw keys
→ 不让采集器拖死比赛环境
```

BAG reset 采用 move 到 `.history` 是为了快，不代表历史目录不占空间。

比赛归档完成后应主动 purge。

---

## 5. 时区必须统一

虚拟机曾使用 America/New_York，导致文件时间与北京时间错 12 小时。

这会直接破坏：
- 录音对时；
- file_changes；
- OJ 提交时间；
- screen；
- Replay 时间线。

赛前应统一检查：
- Windows 宿主机；
- NOI Linux VM；
- 浏览器；
- recorder。

优先统一到 Asia/Shanghai。

---

## 6. 录播系统目标是“恢复过程”，不是“统计按键”

推荐三层：

1. **screen**：当时看到了什么；
2. **timeline**：当时做了什么；
3. **file snapshots**：磁盘上的代码是什么。

raw_keys 只做精确补充。

赛后 AI 应先按时间线“看录像式复原”，按键统计只作为最后辅助。

---

## 7. 赛前真正要验收什么

### BAG
- `doctor.sh`
- T1 真实 sample 冒烟
- `run.sh c` 的 freopen smoke
- Code::Blocks project 只构建 main.cpp

### VM
- 时区
- 磁盘余量
- 鼠标
- 剪贴板
- 无更新弹窗
- Code::Blocks Debug target
- terminal 正常

### 捕捉器
- 输出目录
- screen 分段
- file_changes 真能记录
- 磁盘保护
- 时间戳与 OJ 对齐

---

## 8. 赛后优先打包

1. `contest_capture/`
2. BAG 四题工作目录（包括 debug_*.in/out）
3. OJ 完整归档
4. 录音原文
5. 必要时 VM 快照 / 递归文件清单

不要只给最终四个 cpp。

最终 cpp 只告诉你“比赛结束后剩下什么”，不能告诉你四小时里曾经写过、推倒过、验证过什么。
