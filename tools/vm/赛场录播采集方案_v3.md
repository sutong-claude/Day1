# 赛场录播采集方案 v3

目标不是统计键盘，而是让赛后 AI 能“看比赛录像”。

## 为什么纯键盘日志不够

按键无法唯一恢复屏幕状态：鼠标点击、光标移动、框选、Ctrl+Z、粘贴、输入法、终端输出都可能改变最终画面。因此采用三层证据：

1. **screen**：1 fps 左右 H.264/Matroska 分段录像，负责“我当时看到什么”；
2. **timeline**：活动窗口 + TYPE + KEY + PASTE，负责“我当时做了什么”；
3. **file snapshots**：代码/notes 保存后的真实文件状态，负责“最后文件到底长什么样”。

## 空间原则

- screen 默认 1 fps、CRF 38、20 分钟一段；
- raw EV_KEY 用 gzip；
- 设置目录体积上限和剩余磁盘阈值；
- 触发磁盘保护时先停 screen，保留轻量 timeline；
- 不允许录音/录像临时文件把主机 C 盘拖满。

## 赛后给 AI 什么

优先级：
1. contest_capture 整个目录 zip；
2. 在线录音转写原文；
3. OJ 完整归档；
4. 虚拟机/项目快照。

AI 应先按时间线“看录像式复现”，统计只作为最后辅助。

## 2026-10-07 源码审计补充：不要把 Replay v3 当成无损日志

三包原始资料中的实际 `contest_replay_capture.py` 已做源码级审计，详见：

- `tools/vm/Replay采集脚本_源码考古与能力边界.md`
- `tools/vm/replay_recorder/contest_replay_capture_v3.0.1.patch`

### v3.0.0 已证明的边界

1. **Ctrl+Alt+P 只暂停 semantic timeline/clipboard，没有暂停 raw EV_KEY 持久化。**
   所以 pause 区间出现 raw key，不代表“用户没有暂停”。

2. **FileTracker 没有 initial baseline snapshot。**
   recorder 启动前已存在、后续没改的文件可能不会出现在 `file_changes` 内容链。

3. **FileTracker 是约 2 秒 polling。**
   它是“观察到的落盘状态序列”，不是每一次 Ctrl+S 的事务日志。

4. **会跳过 `sample*` / `attachment*` 等目录及部分文件。**
   因此下载样例、附件、二进制、超大文本要结合 screen/VM 查。

5. **v3.0.0 x11grab 输入端没显式低帧率。**
   已形成 v3.0.1 patch，在 input 端加入目标 framerate，避免可能先高帧率采集再丢帧。

### 推荐证据解释顺序

仍沿用捕捉器自己的读取协议，但增加“通道能力边界”检查：

1. timeline：先确定题目切换、pause/status、显式键盘语义；
2. file_changes：恢复“被观察到”的保存版本；
3. screen：补鼠标、网页、Debugger、未保存状态、sample/attachment；
4. raw_keys：只作精细动作补证，不单独推翻更强文件事实；
5. manifest：检查 recorder version、停止原因、screen guard；
6. 录音/OJ/VM：完成原因与最终交付交叉验证。

**任何两层冲突时，先审 recorder 是否存在采样/排除/暂停语义造成的差异，再归因给选手行为。**
