# 三包原始资料｜全文读取与处理台账

> 目的：防止“列过文件名 / 建过索引 / 看过摘要 / 抽过前中后”被误报成“原件已经全文读过”。
>
> 原始资料池固定为 Library 三包：
> - `模拟赛资料_01_共03包.zip`
> - `模拟赛资料_02_共03包.zip`
> - `模拟赛资料_03_共03包.zip`
>
> **只有真的从首字节/首行连续处理到 EOF 的文本类内容，才允许标 `FULL-RAW-READ`。**

## 1. 状态定义

| 状态 | 含义 |
|---|---|
| `FULL-RAW-READ` | 内容哈希去重后，原始文本/源码从头到尾逐字符/逐行进入本轮读取流程；不是前中后抽样 |
| `STRUCTURALLY-PROCESSED` | 二进制/测试数据/视频等不适合直接塞进语言模型文本上下文，但已完整遍历、哈希、计数、解析元数据或程序化分析 |
| `INDEXED-ONLY` | 已知道路径/大小/hash，但内容还没有完整处理 |
| `NOT-YET-FULL-READ` | 可读文本存在，但还没有完成逐文件 EOF 读取；禁止说“已读” |

## 4. 已结构化处理但不能冒充“全文进上下文”的类别

### 测试数据 `.in/.out`

超过 2,000 个文件，字节量超过 1.1GB。

处理策略：
- 全路径遍历；
- hash / size / provenance；
- 重复检测；
- 按题/归档映射；
- 对需要验证的题再由程序逐实例跑 checker/brute/stress。

状态：`STRUCTURALLY-PROCESSED`，**不是 FULL-RAW-READ**。

原因：把 1GB 数字测试数据逐字符塞进 LLM 上下文没有信息收益，也超过物理窗口；应让程序处理全量数据，而不是文本模型假装“看了一遍”。

### Screen MKV

约 233 段、约 525MB。

当前：

- 尚未把每一帧都视觉审阅。

状态：`INDEXED-ONLY / PARTIAL-VISUAL-READ`。

### PDF

状态：混合；**禁止总称 FULL-RAW-READ**。

## 6. 接下来固定读取顺序

不再“先写总结再找证据”，而按以下顺序逐批闭合：

1. 赛场脚本 / shell；
2. 四场 v3 `file_changes.jsonl` 全文；
3. semantic `timeline.txt` 全文；
4. OJ HTML / record / statement 原文；
5. notes / README / 导读 / AI提示词；
6. raw key JSONL（需要时与 timeline 重解码；不把重复底层事件当高信息文本）；
7. image-only PDF 与 screen 的高争议时段视觉核对；
8. 测试数据由程序全量跑，不靠 LLM 肉眼逐数字读。

每完成一类：
- 本台账改状态；
- 新结论立即 append 到对应比赛《逐段考古纪要》；
- 更强证据推翻旧结论时保留修订链；
- 只有 commit 成功才汇报“仓库已更新”。

## 7. 验收规则

以后如果有人说“这些三包已经全部读过”，必须能回答：
- 哪些类别是 FULL-RAW-READ？
- 唯一内容 hash 数是多少？
- 哪些只是索引/程序化处理？
- 哪些 image/video 尚未逐帧/逐页？
- 结论落到哪个比赛的哪个证据事件？

答不上来就不算“读过”。
