# 3. 代码版本 churn

## Day5

| 路径 | save-like | unique SHA | peak bytes | final bytes |
|---|---:|---:|---:|---:|
| 第一代 `T1/main.cpp` | **48** | **43** | 1373 | 1350 |
| 第二代 `T4(now T1)/main.cpp` | **19** | **18** | 1304 | 1304 |
| `T3/WA.cpp` | 4 | 4 | 1191 | 1185 |

这是四场里最明显的“高 churn 不等于高信息增益”案例：
- 第一代长期在 `multimap / lower_bound / upper_bound / .first/.second` 上来回修；
- timeline 甚至记录了浏览器搜索 `multimap lower_bound`；
- 真正的数学 query 契约——“按位置找第一个值超过阈值者”——到约 03:28 才被口头纠正。

所以 43 个 unique SHA 大量是**实现接口抖动**，不是 43 次数学推进。

约 02:29 发生真正结构性动作：
> 旧 T4 目录被改造成 `T4(now T1)`，从模板重启第二代 T1。

约 03:02 又把官方样例复制进新目录并终端编译/diff。

这才是“模型/工程代际切换”，应该和普通 save 分开计。

## Day6

| 路径 | save-like | unique SHA |
|---|---:|---:|
| A `T1/main.cpp` | 9 | 8 |
| B `T2/main.cpp` | 6 | 6 |
| C `T3/main.cpp` | **31** | **25** |
| D `T4/main.cpp` | 11 | 11 |

对照最鲜明：
- A：8 unique → AC100；
- C：25 unique → 0。

A 的少量版本持续增加不变量并配套验证：
- 手造边界；
- 多个官方样例；
- 大规模 sanity；
- 正式 IO；
- 提交。

C 的大量版本则出现：
- brute 修索引；
- 正确四分类；
- 类别语义压缩；
- 回退；
- 概率输出；
- 最终仍错误 predicate。

因此：
> **“unique SHA 数”是研究活动量，不是学习/得分进度。**

## Day7

| 路径 | save-like | unique SHA | peak → final |
|---|---:|---:|---:|
| A | 8 | 8 | 1598→1598 |
| B | 17 | 16 | 1551→1447 |
| D | **20** | **20** | 1671→583 |

B 的版本链有一个非常健康的动作：
- 1433B stable；
- 1178/1156B 激进重构失败；
- **回滚到完全相同 SHA**；
- 终端重新 `g++ -O2` 并跑/比对官方样例；
- 再复制到 `WA.cpp` 冻结；
- 最终只补正式文件 IO。

所以 B45 的失败重点不是“版本管理差”，而是：
- O(n²) 组件重扫；
- 无用 `unordered_set` 放大资源；
- 没完成 reverse-time + DSU。

D 相反：
- 20/20 unique；
- 多轮 Watches / Console / F9 / 手树；
- 1663B 峰值候选；
- 最后模型被判死，整体推成 583B。

这叫：
> **未证明模型 + 大量实现噪声 = 很难判断当前错在数学还是代码。**

而且更大的机会成本是：赛时已知 D19，却没有先冻结。

## Coderlands

| 路径 | save-like | unique SHA |
|---|---:|---:|
| net | 10 | 10 |
| game | 7 | 7 |
| tree | 12 | 12 |
| core | 3 | 3 |

这里 Ctrl+S 多、F9 相对少，是另一种工程风格：
- 最终 T1～T4 源码都被明确复制到 `ZJ-029658/<task>/<task>.cpp`；
- 正式提交资产的“交付目录”意识很强。

但：
- net 录音明确说“对拍一下”，实际未闭合独立 oracle；
- game 的 7 个版本确实是多轮分类/精确分支修正，不是一次写对；
- tree 12 个版本铺了多个 subtask，但 A 分支为空，链分支仍有节点编号/路径位置混用；
- 约 03:29～03:30 错 sample/data 被复制进 T3/T4，随后直接拿来编译/diff，验证链被污染。

所以 tree0 不能单因归到“样例事故”；正确表述是：
> **代码自身不闭合 + 验证数据污染，两条失败链叠加。**

# 4. 四种典型验证模式

## A. 健康验证：Day6 A

```
手算/边界
→ 模型收敛
→ 编译
→ 官方多样例 diff
→ 大规模 sanity
→ 正式 IO
→ 提交100
```

它最值得复用。

## B. 实现 Debug 很勤奋，但模型没变真：Day6 B

编译/类型/浮点/下标逐步修干净，
但 “fixed average speed” 这个 special predicate 从未被独立反例杀掉。

结论：
> Debug 只能验证“程序是否按模型跑”，不能证明模型。

## C. 正确结构已经出现，却被错误压缩：Day6 C

timeline/file_changes 直接见到四分类与注释语义：
- must light；
- optional；
- impossible / must not light；
- off。

后来为了简化压成单 `cnt`，把不同语义合并。

结论：
> 优化状态前，先问“这些类别未来约束角色是否相同”。

## D. 有验证意识，但没有物化：Coderlands net

录音：
> “我对拍一下。”

实际：
- 未建立可重复 brute + generator + mismatch；
- 随即切 game；
- 最终 OJ100 又掩盖了反例。

结论：
> **想对拍 ≠ 已验证。**

# 5. 新的跨场指标：信息增益事件

以后 Replay 统计不再把每次 save/F9 等权计数。

每个阶段优先记录以下“高信息增益事件”：

1. 新不变量；
2. 新反例；
3. predicate 从必要条件变成必要充分；
4. 正确 brute 形成；
5. 复杂度瓶颈被精确定位；
6. pair relation 被压成单点 key；
7. 删除/分裂被改写成 reverse add/merge；
8. partial 进入 VERIFIED/FROZEN；
9. 失败模型被明确判死；
10. 正式提交副本与工作区 SHA 对齐。

反之以下通常只是低信息 churn：
- 类型修正；
- 拼写；
- .first/.second 来回交换；
- 数据结构容器替换但 query 契约不变；
- 同一个错误模型上的样例 patch；
- 大量保存而没有新的证明/反例。

# 6. 赛中可执行规则

以后出现下面任何一个信号，必须触发动作：

- **连续 3 次修改只动实现，不增加数学证据**  
  → 停 Debug，写当前 predicate 的必要性/充分性或找反例。

- **unique SHA 快速增长但样例状态不前进**  
  → 把当前版本冻结，另开 research 文件；禁止污染 partial。

- **口头说“我知道这 X 分一定能拿”**  
  → 10 分钟内 CODED → VERIFIED → FROZEN。

- **口头说“我要对拍”**  
  → 只有 generator + brute/oracle + 自动 mismatch 真正跑起来才算完成。

- **最终 VM 文件与 OJ source 不同**  
  → 以 OJ source 为提交事实；VM 后续版本仅作为赛后/提交后研究证据。

# 7. 证据边界

本报告是对完整 Replay 文本事件流的统计，不替代 screen：
- 未保存编辑；
- 鼠标操作；
- Debugger 内变量；
- 网页阅读；
- 错 sample 的可视内容；

仍需 screen/VM 交叉。

同样，timeline 中某个按键存在，不等于行为成功；必须和 FILE / terminal output / OJ / screen 互证。
