## 1. Day5 A：赛后代码与哨兵 bug

用户赛后写出 strict next-greater 版本：

- r_i = i + d_i；
- 单调栈求右边第一个 r_j > r_i；
- DP 从右往左。

最初版本有一个非常隐蔽但确定的 bug：

- “不存在 next greater”时用 l[i]=n+1 做 sentinel；
- 但后续 if 没有先排除 n+1；
- 当三角形延伸超过 n+1 时，会把 sentinel 当成真实 blocker。

最小例：
~~~text
n=1
d1=2
~~~

错误版会算成 3，正确应为 4。

修正时要先判断：
~~~cpp
if (l[i] != n + 1 && l[i] < i + d[i]) {
    ...
}
~~~

赛后进一步确认：
- strict > 是一个自然且一致的定义；
- equal endpoint 时斜边重合，后来的同 endpoint 三角形并不会产生新的包络接管；
- 关键不是 > / >= 的表面差异，而是 transition 必须与 chosen next 定义一致。

这次最值得记的是：
**sentinel 不是数据。哨兵值必须在进入普通状态转移前显式排除。**

## 3. Day6 A：真实推理链不能被压扁

赛时并不是“一眼发现 gap 贪心”。

真实过程大致是：

1. 第一眼发现“插入数量”具有单调性，想到二分；
2. 很快发现：就算二分答案 X，也不会构造/判定；
3. 转去看 n=1，得到“一个 a_i 能承受约 a_i-1 个休息日”的容量感；
4. 研究左右边界；
5. 研究相邻工作日之间最多能放多少；
6. 产生“每个 gap 单独取最大”的自然猜想；
7. 用 545 发现左右 gap 会一起撑爆中间工作日；
8. 才真正形成 gap 变量 + 相邻容量约束；
9. 左到右修正时，已经决定的左边不回头，只削右边；
10. 贪心收敛，约 50 分钟首交 AC。

因此 A 的迁移经验不是“记住公式”，而是：

> 局部容量 → 局部独立最优 → 主动找耦合反例 → 发现相邻共享资源 → 单向修正。

## 4. Day6 B：从 DAG 到 LNDS 的真正桥梁是“拖延量”

用户赛时已经想到：
- 日志是点；
- 两点有 compatibility；
- 只向后连；
- 删除最少 = 保留最长链；
- O(m²) pair 检查太慢。

正确下一步不是直接想“LIS 模板”。

更自然的问法：

> 每一条日志相对“理论最快到达这里”，到底多拖了多少时间？

这个“拖延量”如果从 5 变成 2，就意味着后面把已经浪费的 3 小时追回来了，只能超速。

所以合法序列中：
**拖延量只能不下降。**

这时 LNDS 才自然出现。

特殊性质“所有速率相同”：
- 消掉的是“理论最快时间 F(x) 很难算”这一困难；
- 不是推出“全程必须匀速”。

赛时 partial 错就错在把“最大允许速度相同”解释成了“固定平均速度”。

## 5. Day6 C：用户赛时已经想到四分类

这是本次最重要的复盘纠正之一。

replay/file_changes 显示用户赛时真的写过：

1. 同时包含 k-1 与 k；
2. 只包含 k-1；
3. 只包含 k；
4. 两个都不包含。

所以不能再写：
“用户没有想到分类，只写 cnt==k”。

正确差距：

~~~text
四分类已经出现
↓
没有继续给四类赋真正语义
↓
把前两类都压成 cnt++
↓
最终 predicate 退化错
~~~

正确角色：

- 同时含 k-1,k：必须亮；
- 只含 k-1：可选；
- 只含 k：该 k 直接不可能；
- 两者都不含：必须灭。

另一个关键经验：
n<=5 的 10 分最好不要先优化 fixed-k 判定；
直接枚举 2^n 个亮灭 mask、逐灯按题意模拟，才是最稳机械 oracle。

## 6. Day6 D：第二档也是 15 分，不是 1 分

原题子任务表使用 rowspan。

曾经把：

~~~text
2
1
n,q<=1000
~~~

误读成“第二档 1 分”。

实际：
- 第一档：15 分，n,q<=100；
- 第二档：15 分，依赖 1，n,q<=1000。

“1”是依赖编号，不是分值。

用户赛时第一档 brute 数学正确。

第二个 15 分的自然升级：
1. phi 值预处理；
2. pair 分数 O(1)；
3. 所有区间 best[l][r] 预处理；
4. query O(1)。

这也是一个典型经验：
**已有正确 brute 后，先问重复算了什么，不要立刻跳高级算法。**

## 9. C++14 / C++17 名字冲突补充

用户赛时遇到 lcm 等变量名冲突。

结论：

- std::lcm / std::gcd 是 C++17 新增，所以 C++14 与 C++17 确实不同；
- std::next / std::prev 更早已有；
- GNU/Linux 数学库有全局 y1(double)，所以 int y1; 全局声明也可能直接撞；
- pre 通常没这个标准库问题。

竞赛安全命名：
- lc / gc；
- nxt / prv；
- yy / y_1。
