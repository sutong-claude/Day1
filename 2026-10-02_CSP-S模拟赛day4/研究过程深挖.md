# Day4 研究过程深挖

> 重点不是重写题解，而是恢复：赛时到底是怎么想的，为什么会从“有工具”一路走到 0 分。

# 1. Day4 最容易被误解的地方

结果是 0 / 400。

但完整键盘回放证明：
这不是“后半场放弃”。

后半场录音明显沉默，但手上仍然持续：
- 重写 A；
- 整理 / 提交 B；
- 最后写 D。

所以以后不能再用：

> “没说话”

推断：

> “没在思考 / 没在工作”。

这场更准确的状态是：

> **口述和元认知层关闭，但机械执行层还在高速运转。**

这通常是比赛已经进入高压、低质量执行阶段的信号。

# 2. A：其实已经看见了“额外代价来自支撑极值”

## 最早的正确东西

赛时很早得到：

~~~text
ans >= sum |a_i-b_i|
~~~

这是正确 baseline。

后来大样例不匹配时，又明确说出：

> “需要有人撑住最高 / 最低，然后再卸下来。”

这不是随口猜。
它已经在触碰 full 的核心：
除了每个位置自身变化量，还存在为了维持全局极值 / 支撑过程产生的 detour。

## 真正缺的一步

当时一直把“谁来撑”当成动态过程想。

更好的问法应该是：

> 如果最终必须选择一个 support，它的额外代价能否静态写出来？

也就是：
把“操作过程”压成“选择哪个位置承担额外责任”。

Day4 A 的研究价值就在这里：

> **动态过程题如果 baseline 很清楚，而样例只多出一个额外代价，先找“谁在承担这个额外代价”，再把它静态化。**

## 最终提交为什么仍然 0

即使 CE 修掉，
n=1 分支仍然无条件输出 -1。

当 a1=b1 时答案应为 0。

这说明最后阶段已经不再是：
“模型研究”。

而是：
“从残局赶一个能交的版本”。

# 3. B：Day4 真正最重要的一题

这题不是因为拿了分。
而是第一次完整展示：

~~~text
generator
+ brute
+ candidate
+ diff
~~~

都已经存在，
结果研究仍然会错。

为什么？

因为 oracle 本身漏条件。

## 第一层：输入 / 工程错误

solve2 又读一遍输入，
导致流错位。

这是局部实现问题。

## 第二层：oracle 漏题意

删除值 v 不能等于窗口两个端点值。

brute 没检查这一条。

于是：

> “candidate 和 brute 一致”

只能证明：

> 两份代码共享同一个错误题意。

这是 Day4 最重要的验证教训：

> **对拍之前先验证 oracle 的题意覆盖，而不是先验证 candidate。**

建议以后 brute 顶部直接写：

~~~text
[ ] 输入约束
[ ] 操作约束
[ ] 端点约束
[ ] YES 条件
[ ] NO 条件
[ ] 最优性
~~~

逐项打钩。

## 第三层：full 状态本身不闭合

原题类似：

> 窗口里是否存在一个可删除值 v，使条件成立。

赛时滑窗想维护：

~~~text
当前 v
当前 count
last / least / map
~~~

问题：

当左端点右移时，
原本可行的 v 可能失效，
新的最优 v 可能是完全不同的值。

也就是说：

> 未来需要的信息，不是“当前这一名候选 v”的局部状态。

这就是状态不闭合。

## 应该怎么从这里醒过来

一旦发现：

> “删左端点后，我不知道新的 v 从哪里来。”

不要继续加字段。

应该回到量词：

~~~text
存在 v
使窗口合法
~~~

尝试交换：

~~~text
固定一个 v
它允许哪些窗口？
~~~

这类“存在一个隐藏参数”的窗口题，
固定参数再研究往往比直接维护 existential witness 更自然。

# 4. 为什么 Debug 会进入黑洞

T+2:30～3:03，
键盘动作大量变成：

- c；
- last；
- least；
- map；
- 局部条件；
- 复制粘贴；
- 修一处又加一处。

但几乎没有新的数学事实。

这就是现在定义的：

> **低信息增益 Debug。**

如果今天重打，
这里应该执行：

~~~text
停止写代码
→ 写一句当前状态到底表示什么
→ 删除左端点后，状态是否还能从旧状态恢复？
→ 如果不能，宣布滑窗假设失败
→ 回 brute / partial / 切题
~~~

不是继续“给状态补字段”。

# 5. C：最大的损失不是没做出来，而是没得到正常阅读时间

C 有很强的小状态 / bitmask 信号。

但 A+B 把主要时间吃掉后，
C 基本没有获得一次完整建模窗口。

这属于另一种比赛失败：

> **前题并没有 AC，却把后面更适合自己的题型彻底饿死。**

所以“扫完四题”不是形式主义。

它的意义是：
先知道后面有没有：
- 更熟的模型；
- 更便宜的 partial；
- 更强的子任务信号。

---

# 6. D：最后阶段没有稳定资产可以回滚

最后已经进入抢交。

从键盘看：
- 先写 n! fallback；
- 再补 DFS；
- 再补排列 / 连通判断；
- 直到 replay 结束仍没稳定。

这说明最后阶段最危险的不是“没时间”。

而是：

> **没有早先冻结的 D partial 可以退。**

这正是后来 score bank / frozen partial 规则的来源之一。

---

# 7. 环境事故应该怎么评价

主机 C 盘被录制临时文件挤爆，
VM / recorder 都受影响。

这件事是真实的。

但赛后重交证明：
就算机器不崩，
当前代码也未必有分。

所以正确归因是：

~~~text
模型 / oracle / 交付问题 = 根因
环境事故 = 放大器
~~~

不能用环境把数学问题盖掉，
也不能反过来假装环境没影响。

# 8. Day4 留给后面的真正资产

Day4 虽然 0 分，
却催生了很多后续真正有价值的东西：

- generator / brute / diff 体系；
- oracle 条款检查；
- frozen partial；
- 信息增益止损；
- replay / keyboard 恢复；
- raw keys 隐私规则；
- 录播磁盘 guard；
- BAG 稳定版 / 实验版分离；
- 量词交换；
- 状态闭合检查。

所以它不是“毫无产出的一场”。

更准确：

> **比赛分数归零，但工程和研究方法在这场完成了一次大升级。**
