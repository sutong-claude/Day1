## E-D4-011｜T1/checker.cpp 名称纠偏｜它不是题目 checker，只是 mismatch counter

**来源**：三包全量展开后的原始 `T1/checker.cpp` 完整源码。

它实际只做：
1. 读 n；
2. 读数组 a[1..n]；
3. 读数组 b[1..n]；
4. 若 b[i]==-1 则跳过；
5. 否则统计 a[i]!=b[i] 的位置数并输出 cnt。

它：
- 不使用 testlib；
- 不读取题目状态/操作语义；
- 不验证 candidate 可行性；
- 不验证最优性；
- 把 b[i]=-1 的位置直接忽略。

所以以后这个文件必须分类为：

> **local comparison utility / mismatch counter**

而不是：
- official checker；
- brute oracle；
- correctness validator。

**新证据规则 [P/source]**：
> 文件名叫 `checker.cpp` 不能自动获得 checker 权威，必须先审计它实际验证的命题。

## E-D4-013｜B 对拍污染链闭合｜非法 generator + 错 oracle 同时存在

**来源**：
- 三包原始 `T2/gen.cpp`
- `T2/AC.cpp`
- `T2/WA.cpp`
- `T2/duipai.sh`
- 现场残留 `1.txt / 2.txt / 3.txt / notes.txt`
- 2026-10-07 独立真 oracle + 原版程序全穷举

完整报告：
`原始材料/T2_对拍污染链_非法generator_错oracle.md`

### generator 已被 [P/source] 证明违反题面域

题面：
```
1 <= a_i <= n
```

gen：
```cpp
n = Rand(1,10);
a_i = Rand(1,13);
```

按 generator 自己的随机分布，完整 case 合法概率只有约 **2.83%**。

更关键：赛场目录最后留下的实际 diff case：

```
n=7
1 3 10 7 4 8 10
```

本身就违反 a_i<=7。

所以：
> **赛时对拍确实已经被非法输入污染，不是赛后理论猜测。**

### AC oracle 已被 [P/source] 证明遗漏题面硬条件

题面要求：
```
v != a_l
v != a_r
```

AC.cpp 完全没检查两条端点限制。

最小反例：
```
n=1, a=[1]
flawed AC=1
truth=0
```

### 合法域上也不是“小误差”

把原版 AC / WA 与独立真 oracle 对所有：
```
n<=6
a_i in [1,n]
```
共 **50,069** 个合法输入穷举：

- oracle!=truth：34,418（68.74%）
- candidate!=truth：34,789（69.48%）
- false green：22,075（44.09%）
- false red：6,187（12.36%）

其中：
- false green = candidate 和错 oracle 一致，但都错；
- false red = candidate 实际正确，却被错 oracle 判成 diff。

因此 E-D4-003 的“oracle 自己漏端点”需要升级成更强结论：

> **Day4 B 的 stress 信号本身在 generator-domain 和 oracle-contract 两层同时失真。后续 Debug 既可能在修真 Bug，也可能在追工具制造的幻觉。**

这解释了为什么后续大量局部 patch 并没有稳定提高信息增益。

### 新硬规则

“真对拍”必须同时回答：
1. generator 是否只生成题面合法域？
2. oracle 是否覆盖题面所有必要条件？
3. candidate/oracle 的比较是否在同一个语义对象上？

四个文件齐全 ≠ 对拍闭合。

### 修订后的研究过程

旧式一句话：
> “A 猜过答案就是 L1，然后发现不对。”

太粗。

```
H1: ans = Σ|a_i-b_i|
↓
自己写出必要下界

↓

↓

```

> 上层“等号总能达到”失败，不应把下层“lower bound 必然成立”一起丢掉。

因此 A 的训练点应从“别瞎猜公式”升级为：

## E-D4-012｜B 正式提交的小数据 brute 分支本身会二次读输入

**来源**：
- OJ submitted source = VM `Day4/T2/main.cpp` exact；
- P5598 原始题面；
- VM 原始 `T2/1.txt` 与参考 `2.txt`；
- 2026-10-07 本地原样编译复现。

题面 #1：
> Σn≤20，15分。

正式 source 的外层已经：

```cpp
cin >> n;
for (int i=1;i<=n;i++) cin >> a[i];
if (n <= 20) solve2();
```

但 `solve2()` 开头又写：

```cpp
int n;
cin >> n;
for (int i=1;i<=n;i++)
    cin >> a[i];
```

也就是说：
> **每一个 n≤20 的 case 都会在进入 brute 前再次从输入流读取“下一份 n + 数组”。**

这不是复杂度问题，而是确定的输入流错位 [P/source]。

### 原样样例复现 [E]

VM：
- `T2/1.txt`：1组，n=7，数组 `1 3 10 7 4 8 10`
- 同目录 `2.txt`：参考答案 `4`

本轮：

1. 正式 submitted source 原样 `-O2` 编译；
2. 将 `1.txt` 作为 `Resonance.in`；
3. 1秒 timeout 运行。

结果：
- **timeout（rc=124）**
- `Resonance.out` 为空。

控制实验只删掉 `solve2()` 的第二次输入：
- 其他 brute 逻辑完全不变；
- 同一 `1.txt`；
- 正常结束；
- 输出 **4**，与参考一致。

### 为什么会表现成 TLE / UB

单 case 输入中：
- main 已经把唯一 case 全部读完；
- solve2 再执行 `cin >> local_n` 时 EOF；
- 局部 `int n` 没有被成功赋值；
- 后续循环使用未初始化值，进入未定义行为；本机复现为超时。

多 case 时则会直接吞掉下一组测试，造成整体 case boundary 失步。

### 修订结论

旧的：
> “Day4 B 有一个 n≤20 brute，但后面 full 模型/复杂度失败。”

应改成：

> **submitted bytes 的 n≤20 分支连输入契约都没有闭合，不能把15分计入‘已编码可冻结资产’。**

因此 Day4 B 的机会成本分类更准确是：
- brute 思路/代码主体存在；
- 但 delivery identity + input contract 未验证；
- **NOT_FROZEN**；
- 官方 #1 实际 TLE0 与该 bug 完全兼容。

这也再次说明：
> “写了 brute.cpp / solve2” ≠ “拥有可提交 partial”；只有拿正式输入格式独立跑过，才进入 VERIFIED/FROZEN。


## E-D4-013｜B 小暴力并非数学错｜standalone→正式入口移植时发生 input-ownership regression

**来源**：

- 正式 `main.cpp` / OJ submitted source；
- 同一原样 `1.txt`。

进一步控制实验：

`AC.cpp` 的结构是：

```cpp
while (t--)
    solve();

solve() {
    int n;
    cin >> n;
    read a[];
    ... brute ...
}
```

它在原样 `1.txt` 上：
- 正常退出；
- 输出 **4**。

后来集成进正式代码时，入口改成：

```cpp

    cin >> n;
    read a[];

```

但从 standalone brute 搬来的 `solve2()` 仍保留：

```cpp

cin >> n;
read a[];
```

于是产生“双重读入”。

### 根因分类

这不是：
- brute 数学模型错误；
- 单纯复杂度错误；
- checker 错。

而是：

> **FUNCTION_TRANSPLANT_CONTRACT_FAILURE：函数从“拥有输入”改成“消费已读状态”时，接口契约没有同步修改。**

这是一类很值得单独记住的工程 Bug，因为局部看：
- standalone brute 对；
- optimized solve1 也可能能跑；
- 两者各自函数体都“看起来合理”；
- 真正错误只存在于**组合入口**。

### 新交付规则

把已验证 partial 嵌入正式程序后，冻结状态必须重新经过：

```
standalone VERIFIED
→ integrate dispatch/main
→ INTEGRATION_UNVERIFIED
→ 用原样文件输入重跑
→ INTEGRATION_VERIFIED
→ 才能提交
```

“这个 solve2 我之前单独测过”不能继承到新的 main 接口。


## E-D4-014｜B solve1 最小模型反例｜候选滤波值被允许等于右端点

**来源**：
- P5598 原始题面；
- notes 中的 `t/mp` 状态草图；
- 正式 submitted source 的 `solve1()`；
- 2026-10-07 独立 brute + 原程序实跑。

题面有一个非常容易被滑窗状态漏掉的硬条件：

> 选中的滤波频率 v 不能等于窗口两个端点：
> `v != a_l` 且 `v != a_r`。

### submitted solve1 的状态转移

当加入新的右端点 `a[r]` 造成非递增，而当前还没有候选 `c` 时：

```cpp
else if (c == -1) {
    if (a[r] > a[least]) {
        c = a[last];
        last = r;
    }
    else {
        c = a[r];
    }
}
```

第二个分支直接：
> `c = a[r]`

这等价于允许：
> **把新加入的右端点自身当成滤波频率删掉。**

题面明确禁止。

### 极小概念反例

```text
[2, 3, 1]
```

solve1 的逻辑会：
- 2 < 3，继续；
- 加 1 时发现下降；
- 令 `c=1`；
- 于是把长度3窗口视为可行。

但若窗口是整个 [1,3]：
- v=1 会删除右端点，非法；
- v=2 会删除左端点，非法；
- v=3 删除中间后剩 2,1，不递增。

真实答案只有2。

### 直接落在官方 #2 的 n=21 反例

为确保不是“n≤20 会走另一个分支”的人工反例，本轮构造：

```text
n = 21
2 3 4 5 ... 21 1
```

所有值互不相同，**正好满足 subtask #2 的特殊性质**，且 n>20，正式程序会走 `solve1`。

独立 brute：
- true answer = **20**

理由：
- [1,20] = 2..21 严格递增；
- 可选全局存在、但在窗口外的 v=1，合法得到长度20；
- 整段21若不删末尾1就有下降；
- 唯一能修该下降的 v=1 恰好等于右端点，被题面禁止；
- 因而长度21不可能。

正式 submitted source 原样运行：
- output = **21**

因此这是 [E] 可复现的确定反例。

### 这条反例解释了什么

OJ：
- subtask #2：所有 a_i 互不相同；
- verdict = WA0。

现在可以给出一个非常具体的模型级解释：
> **即使没有重复值，solve1 仍会把窗口端点错误当成可滤候选，因此“all distinct”并不能救这套状态。**

### notes 状态谱系的真正缺口

早期 notes 写：
```text
mp[a_i] absent → t=a_i
...
a[l] == t && mp[t] == 1 → t=-1
```

重点一直在：
- 当前是否已经出现一个“坏值”；
- 坏值在窗口里还剩几次；
- 删掉它后是否递增。

但没有把题面的另一个状态契约显式写进来：

```
candidate_v != left_endpoint
candidate_v != right_endpoint
```

于是后面的 `t → c → last/least` 代码虽然越来越复杂，**一个最初遗漏的合法性条件始终没有进入状态定义**。

这就是为什么“变量更丰富”没有让模型闭合。

Day4 B 至少有两类独立问题：

1. **n≤20 / solve2**：
   - standalone brute 数学可用；
   - 集成 main 后重复读输入；
   - 属 FUNCTION_TRANSPLANT_CONTRACT_FAILURE。

2. **n>20 / solve1**：
   - 输入接口正常；
   - 状态模型允许过滤端点；
   - 属 MODEL_INVARIANT_MISSING。

因此 0 分不能压成一个“Debug没调好”标签。

> **partial 集成契约错 + full 状态不变量缺失**

## E-D4-013｜B 对拍为什么会“假绿”｜oracle 与 candidate 共享同一个 endpoint 漏项

**来源**：
- VM `T2/AC.cpp`
- VM `T2/WA.cpp`
- `T2/gen.cpp`
- `T2/duipai.sh`
- 原题端点约束
- 2026-10-07 最小反例重放

E-D4-003 以前只写：
> oracle 自己漏了端点条件。

现在可以把因果链进一步钉死成 **common-mode failure**。

### oracle 的具体漏项 [P/source]

题意要求选择被滤掉频率 `v` 时：

```
v != a_l
v != a_r
```

但 `AC.cpp` 的 brute 只是：

```cpp
for (int k=1;k<=n;k++) {
    vector<int> v;
    for (int x=i;x<=j;x++)
        if (a[x] != a[k])
            v.push_back(a[x]);
    check v strictly increasing;
}
```

也就是说：
> 它允许把左右端点本身删掉。

### 最小反例 [E/X]

```text
1
2
2 1
```

真实定义：

- 长度2窗口 ([1,2])：
  - 若删 2，删的是左端点，非法；
  - 若删 1，删的是右端点，非法；
  - 全局没有第三个频率可选；
  - 所以长度2不可行。
- 长度1窗口：
  - 例如 ([1,1])，取全局出现过的 v=1；
  - v≠a_1=2，保留序列 [2]；
  - 合法。

因此正确答案 = **1**。

实测：

```
AC.cpp oracle = 2
WA.cpp candidate = 2
```

### 为什么对拍一定发现不了这类错

`duipai.sh`：

```sh
./gen > 1.txt
./AC < 1.txt > 2.txt
./WA < 1.txt > 3.txt
diff -w 2.txt 3.txt
```

只比较 candidate 与 oracle。

而 generator：
- n 随机 1..10；
- a_i 随机 1..13。

所以 `[2,1]` 完全在 generator 定义域里。

即使 generator 真生成这个反例：

```
真实答案 1
oracle 2
candidate 2
diff 相等
→ "right on test"
```

### 更强的闭环

E-D4-011 的 n=21 full 反例：

```
2 3 4 ... 21 1
```

`solve1` 在最后一个 1 处执行：

```
c = a[r] = 1
```

并把整个长度21窗口接受。

也就是说 candidate 的 full 模型**恰好也在允许删除右端点**。

因此不是：
> oracle 一个 bug + candidate 另一个 bug 恰好碰巧。

而是：
> **两者共享同一个错误数学假设。**

### 长期规则升级

“对拍要有独立 oracle”还不够具体。

真正要问：
> candidate 与 oracle 是否由同一个自然语言 predicate / 同一个推导写出来？

如果两边共享建模假设，哪怕代码完全独立，也会产生 common-mode error。

推荐对拍 oracle 的独立性层级：

1. **最好**：直接按题面定义枚举所有动作/状态；
2. 次好：用不同数学刻画，并先用手算 sanity cases 校验；
3. 最危险：把 candidate 的核心 predicate 换成暴力循环再写一遍。

Day4 B 就是第3种的标准事故。

## E-D4-013｜D 三代 predicate 连续漂移｜赛后 VM 也没有真正修好

**来源**：
- 正式 submitted source 中被注释掉的旧 DFS；
- VM 后续 `Desktop/D/main.cpp`；
- 独立 exact oracle：
  `工具/D_组合题_三代判定最小反例.py`

### 真命题 [P]

对某个排列，维护前缀并集 ([L,R])。

加入新区间 ([l,r]) 后，前缀并仍连通，当且仅当：

```
[l,r] 与 [L,R] 有交
<=> not (r < L or l > R)
```

这可以直接作为 n≤8/9 的排列枚举 oracle。

### 第一代：端点覆盖 predicate [X]

正式源码里旧 DFS（虽然提交时被注释）做的是：
- 把每个已选区间的左右端点塞进 set/map；
- 维护当前最小端点 mi / 最大端点 ma；
- 要求 `mi..ma` 的**每个整数都至少作为某个区间端点出现过**。

它把：
> 区间覆盖了中间实数点

错误替换成：
> 每个中间整数必须恰好出现成某个端点。

干净反例：

```text
n=3
[1,3]
[1,3]
[1,3]
```

任何排列都好：
- 单个 [1,3] 本身连通；
- 后面继续加相同区间仍连通；
- 正确答案 6。

旧 DFS 在第一个前缀就发现：
- endpoints = {1,3}
- 整数 2 不在 endpoints

于是把所有排列都判坏：
- 旧 DFS = 0。

### 第二代：公共交集 predicate [X]

赛后 VM `Desktop/D/main.cpp` 又把 DFS 改成：

```cpp
L=max(L,l[d[i]]);
R=min(R,r[d[i]]);
if(L<=R) ans++;
```

而且它只在完整排列结束后检查一次。

这等价于：
> **只有所有 n 个区间存在共同交点，才把全部 n! 个排列都算好。**

但题目只要求：
> 每个前缀的**并集连通**，
不是“所有区间共同相交”。

最小规模 n=3 已有反例：

```text
[1,1]
[1,2]
[2,2]
```

真实好排列数 = 4：
- 1→[1,2]→3
- 3→[1,2]→1
- [1,2]→1→3
- [1,2]→3→1

但三个区间没有共同交点：
- post-VM predicate = 0。

### 三代错误对照

```
submitted active path:
任何数据 → n!                 [过松]

submitted old DFS:
并集连通 → “所有整数都出现成端点”  [错误替代对象]

post-VM DFS:
并集连通 → “所有区间公共交集非空”  [过强]
```

这是一条很有价值的模型漂移链：
> Debug 一直在换 predicate，但从未先固定“前缀并连通”的最小可执行定义。

### 下一场触发器

遇到几何/集合性质：
- 连通；
- 相交；
- 覆盖；
- 公共交；
- 端点覆盖；

这些词绝对不能互相替换。

写优化前先拿 n≤7 的 exact oracle 自动对拍 predicate；
只要 predicate 还在换，先不谈复杂度。
