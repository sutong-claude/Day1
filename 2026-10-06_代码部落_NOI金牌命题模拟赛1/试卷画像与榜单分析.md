# 试卷画像与榜单分析（实时榜单校正版）

> **重要纠正：** 这份榜单是比赛仍在开放/分批开始时的快照。54 行账号中，大量 0 分账号当时**尚未开始比赛**，不能把它们当作“打完得到0分的参赛者”。

# 1. 能确定什么，不能确定什么

## 能确定

当时平台榜单快照显示：
- 榜单共有 54 行账号；
- 本人当时总分 200；
- 页面显示排名 **第3/54**；
- 当时前两名 220、210；
- 当前已经出分的账号里可看到若干 net/game/core/tree 得分。

这些是**实时榜单事实**。

## 不能据此确定

不能用 54 行直接计算：
- 最终参赛人数；
- 完赛人数；
- “零分率”；
- 全体平均分；
- 中位数；
- 最终题目 AC 率；
- 最终难度分布。

旧版报告把39个0分行算进均分/中位数，这是错误统计口径，现删除。

# 2. 第3/54 应怎样解释

正确说法：

> **在当时这个榜单快照里，页面排名为3/54。**

它是一个很好的实时成绩信号，但不是：

> “54个已经完整打完4小时的人里第3”。

原因：
- 比赛采用可在不同时间开始的形式；
- 部分账号当时还没开赛；
- 0分行不能自动解释成“参赛后0分”。

因此阶段能力分析不能把实时排名百分位过度量化。

# 3. 仍然可以看的：已出分账号横截面

当时快照中已有若干非零结果。

这只能用于：

> **观察当前已经开始/出分的人里，哪些题暂时更容易形成分数。**

不能外推成最终 AC 率。

例如快照当时：
- game 已出现较多100；
- net 也有少量100；
- core/tree 非零较少。

这说明后两题至少对**当时已出分的一批选手**更难兑现，但不够支持“全场最终只有几人会做”的结论。

# 4. 试卷本身仍然能从题面/赛制分析

不依赖榜单，仍能确定：

## 传统 OI 交付感很强

规则要求：
- 考号目录；
- 四题英文子目录；
- cpp 文件名严格；
- traditional file IO；
- C++17/O2/static；
- 四小时；
- 赛后统一评测。

这一点比代码源在线 OJ 更接近线下 OI 文件交付。

## 子任务捆绑影响策略

tree 的评测明确体现：
- 一个 subtask 里只要一个测试失败，整包可能归零。

所以“raw tests过很多”不能等价于“partial很多”。

这是赛制层事实，与最终参赛人数无关。

# 5. 题目质量和数据质量必须拆开

## net

最终官方100代码存在三点链 M=1 最小反例。

因此：
- 题目思维价值可以高；
- 这一次隐藏数据对实现边界的覆盖有明确缺口。

## game

最终代码：
- OJ100；
- n≤7 全穷举145,636实例0 mismatch。

且 Replay 能恢复多轮 Bug 修复。

这是目前证据最完整的一题。

## tree

不能简单评价“数据卡得很好”：

- 最终代码确实有真实漏洞；
- 但赛时用于验证的下载样例包又出现**格式不匹配**事故；
- 因此“为什么比赛时没修出来”必须同时分析代码和环境验证链。

# 6. 这场200分应如何比较

不能写：

> “200分 > Day7 145，所以能力提升55。”

两套体系：
- 评分方式不同；
- 题目分布不同；
- 榜单快照口径不同；
- 新体系 tree 有整组捆绑。

更合理的比较指标：

- 前两题是否完整闭合；
- 每题研究时间；
- 是否主动切题；
- partial 是否形成完整子任务；
- 验证链是否可靠；
- 文件交付是否稳定。

这场最强的证据是：

> **net/game 两题最终都形成官方100；game还经过独立穷举。**

# 7. 以后榜单分析的硬规则

看到“0分账号”先问：

1. 比赛是否统一开赛？
2. 是否可以随时开始？
3. 这个账号已经开始了吗？
4. 榜单是实时还是最终？
5. 0 是“已打0分”还是“尚无记录”？

没有回答这五个问题前：

> **禁止算平均分、中位数、非零率和最终难度分布。**
