# 3. net 的“推倒重建”不仅是录音说说

45–75分钟键盘仍保持高强度；file_changes 同期显示：

```text
1446B
→ 796B
→ 764B
→ 703B
→ 1586B
→ 1654B
→ 1715B
→ 2306B
```

这是一条非常明确的：

> **删除旧模型 → 从小骨架重建新模型**

而不是最终代码一次性长出来。

# 4. game 的 Bug 修复密度很高

90–135分钟是全场最连续的高代码活动区之一。

尤其 90–105分钟：
- 2,136 keydown；
- 223 Backspace；
- 362方向键。

这和 Replay 里第一版大分类不断编辑吻合。

105–135分钟继续保持高活动，并出现 F9、保存高峰；录音同期：
- 第28组 mismatch；
- k=2改 exact；
- 漏 return；
- 僵尸代码；
- k>=4/5；
- prefix off-by-one。

所以“game100”如果只写最终代码，会把最有训练价值的调试过程全部抹掉。

# 5. core 为什么只有3个小文件

150–165分钟 raw_keys 为0。

结合录音，这段主要是：
- 读核心串定义；
- 识别 Trie；
- 想 EMPTY / L=0；
- 评估 full 成本。

所以源码少不是“没思考”，而是：

> **研究停留在数学/阅读层，没有进入实现层。**

# 6. tree 是真正的后半场编码主战场

165–210分钟连续三个15分钟窗口共：

- 4,622 次 keydown；
- 457 次 Backspace；
- 542 次方向键。

file_changes 同期 T4 从521B涨到4871B。

这说明 tree 的0分绝对不能写成：

> “最后随便写了点 special。”

实际上是：

> **一小时左右高强度铺 N≤5000 / A / 星形 / 链，然后因为每包都有未闭合问题，加上错误格式 sample 进入验证链，最后全部没兑现。**

# 7. 保存行为

Ctrl+S 约72次，明显高于 Day7。

特别高密集：
- net约66分钟；
- game约108分钟；
- game/tree过渡与后半场；
- 219～222分钟交付阶段。

这说明这场的版本/保存习惯比早期比赛成熟得多。

但“保存多”不等于“子任务冻结”：

> 多个 T4 保存状态都只是同一个不断修改的 main.cpp，并没有为每个已闭合 partial 留独立 `partial_XX.cpp`。

# 8. 捕捉器给出的真正结论

raw_keys + file_changes + 录音让四题模式非常清楚：

```text
net  : 研究 → 编码 → 推倒 → 重建
game : 分类 → 高强度编码 → 反例 → 连续修复
core : 低键盘，高思考，未实现
tree : 高强度多special实现 → 验证链事故 → 0分
```

这比单看最终四个 cpp 准确得多。
