# Day4 B 与 Day5 A：两次“调崩”的共同根因

## Day4 B

最终代码有三层问题。

### 1. 小数据分支重复读输入

main 已经读过 n 与 a：
```cpp
cin >> n;
for (...) cin >> a[i];
if (n <= 20) solve2();
```

但 solve2 又：
```cpp
int n;
cin >> n;
for (...) cin >> a[i];
```

于是 n<=20 时输入整体错位；读到 EOF 时局部 n 甚至可能保持未定义值，随后循环可出现异常时间行为。

### 2. brute/oracle 漏题意

题目要求删除值 v 不能等于窗口两端 a_l/a_r。
暴力只做“删掉所有等于 a[k] 的元素再检查递增”，没有端点限制，因此 oracle 本身会把非法窗口判合法。

### 3. 满分滑窗状态不闭合

solve1 用 c / last / least / map 试图维护“当前删除哪个 v”。
但左端点移动时最优 v 可能整体更换，不存在 O(1) 的局部恢复规则。
所以 if/下标本身并不是核心 bug；是这些变量已经不再代表一个自洽数学状态。

## Day5 A

真正需要的是：
`first j>i with (j+d[j]) >= (i+d[i])`。

却先后写成：
- multimap 中按 endpoint 值 lower_bound；
- 无序 vector 上 upper_bound/lower_bound；
- endpoint -> index 的 unordered_map。

这些都没有回答“最小位置 j”。

## 为什么体验上都像“代码不听话”

因为脑内期待的是数学对象 X，代码变量维护的是另一个对象 Y。

断点里看到条件不进、iterator 不是预期、变量又变化，并不是 CPU 不按代码执行，而是：
> **程序非常忠实地执行了 Y，只是 Y 从来没有等价于 X。**

这类问题不能靠再多单步调试解决，必须返回模型层重新写：
- 我真正要查询什么？
- 哪个量有序？
- 删除/加入一个元素后状态是否闭合？
- 有没有最小反例证明维护规则错误？
